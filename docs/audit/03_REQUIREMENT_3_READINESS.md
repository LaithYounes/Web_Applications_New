## 2. توليد بيانات اصطناعية كبيرة

### الموجود

- `DemoCatalogSeeder`: 5 فئات × 15 منتجاً مع صور ومخزون عبر gRPC.
- `DemoUserSeeder`: 10 حسابات.
- `DemoOrderSeeder`: بضعة طلبات عبر المسار الحقيقي (حجز مخزون).
- قيود seed على بيئات `local|testing` فقط + قفل Cache.

### القيود عند توليد مئات الآلاف من الطلبات

1. إنشاء الطلبات عبر `OrderService::createOrder` سيضرب gRPC لكل طلب → بطيء وغير مناسب لتوليد ضخم.
2. المفاتيح الأجنبية: كل `order_items.product_id` يجب أن يشير لمنتج موجود؛ `orders.reservation_id` unique.
3. حجوزات المخزون الحقيقية ستستهلك الكميات أو تتطلب مخزوناً اصطناعياً هائلاً أو تجاوز مسار الحجز للتوليد فقط.
4. فهارس حالية مفيدة: `(user_id, created_at)` على orders؛ `(category_id, created_at)` على products — قد تحتاج مراجعة بعد التضخم.

### نهج آمن معزول (توصية تخطيطية)

1. أنشئ قاعدة/مجلد Docker منفصل أو أسماء قواعد `ecommerce_main_perf` / `ecommerce_inventory_perf` **دون** لمس أحجام demo الحالية.
2. استخدم أمر Artisan مخصّص أو سكربت SQL يُدرج دفعات (`bulk insert`) لـ users/orders/order_items مع `reservation_id` اصطناعية، **بدون** استدعاء gRPC، مع توثيق أن مسار التوليد للأداء فقط.
3. للمخزون: إمّا كميات ضخمة عبر `InitializeStock/AddStock` دفعة واحدة، أو ترك اختبارات القراءة التي لا تحتاج مخزوناً منفصلة عن اختبارات الكتابة.
4. لا تشغّل التوليد على قاعدة العرض التقديمي للجنة دون نسخة احتياطية/حجم منفصل.

## 3. الاستعلامات البطيئة ومخاطر N+1

### ما هو محمي حالياً (Verified by source code)

| المسار | التحميل المسبق |
| --- | --- |
| قائمة المنتجات | `with('category')` |
| تفاصيل منتج | `with('category')` |
| طلبات المستخدم | `with('items')` |
| كل الطلبات (admin) | `with(['user','items'])` |
| السلة | `load('items.product.category')` |
| الفئات | `withCount('products')` |

### مرشّحات للتحليل (Potential — تحتاج قياس)

| المرشّح | السبب | أين |
| --- | --- | --- |
| `GET /products` مع صفحات كبيرة على جدول ضخم | `latest()->orderByDesc('id')` + فلتر فئة؛ يعتمد على الفهرس | `ProductService::getAll` |
| `CategoryService::getAll` + `withCount('products')` | عدّ مرتبط بكل صفحة فئات | CategoryService |
| `CartResource` حسابات PHP للمجاميع | ليس N+1 إن حُمّلت العلاقات، لكن تكلفة CPU مع سلال كبيرة | CartResource |
| `DemoOrderSeeder` تطابق الطلبات في الذاكرة | بطيء عند كثرة طلبات المستخدم | Seeder فقط |
| غياب فهرس على `order_items(order_id)` صريح | FK عادةً يفهرس في MySQL InnoDB — تحقق بـ `SHOW INDEX` | migration |
| قائمة منتجات بدون covering index للفرز المستقبلي | عند إضافة sort بـ price/name | مستقبلي |

### N+1

لا يوجد مسار واضح حالياً يحمّل علاقات داخل حلقات بدون `with` في المسارات الرئيسية.  
**تحذير:** أي إضافة لاحقة لـ `available_quantity` داخل قائمة المنتجات عبر gRPC لكل عنصر ستكون كارثة أداء (N استدعاءات شبكية) — لا يُنصح بها؛ إن لزم التجميع فـ batch RPC جديد في العقد.

### ما يجب قياسه قبل التحسين

1. `EXPLAIN ANALYZE` لـ:
   - منتجات حسب `category_id` مرتبة بـ `created_at/id`
   - طلبات مستخدم بـ `user_id` + `created_at`
   - طلبات admin مع join/user
2. Laravel Debugbar / `DB::listen` لعدّ الاستعلامات على `GET /orders` و`GET /cart` و`GET /products`.
3. قياس زمن `GET /products/{id}` شاملاً gRPC مقابل بدونه.

## 4. Read Replica

### الواقع الحالي

- محرك أساسي: **MySQL 8.4** لـ Laravel.
- اتصال واحد في Compose (`DB_HOST=mysql`).
- لا `mysql.read` / sticky / replica في `config/database.php` المستخدم فعلياً.

### الجدوى المحلية

MySQL يدعم replication (مثلاً replica حاوية ثانية بـ `server-id` وbinlog). يمكن إضافة خدمة `mysql-replica` في Compose لاحقاً.

### اتساق read-your-writes بعد إنشاء طلب

بعد `POST /orders` يجب أن يرى المستخدم طلبه فوراً في `GET /orders` حتى مع تأخر النسخ.

آليات مناسبة لهذه المعمارية:

1. **Sticky / primary بعد الكتابة (موصى بها أولاً):** استخدام `DB::connection('mysql')` للكتابة، وقراءة المسارات الحساسة للمستخدم من الـ primary لفترة قصيرة، أو `Illuminate` sticky database إن فُعّل على الاتصال.
2. **توجيه صريح:** `OrderController@index/show` و`Cart*` يقرآن من primary؛ القوائم العامة للمنتجات يمكن أن تقرأ من replica.
3. **لا تعتمد على** أن replica فورية في Docker المحلي دون قياس `Seconds_Behind_Source`.

المخزون أصلاً خارج MySQL؛ الـ replica لا تحل اتساق الكميات — تبقى عبر gRPC.

## 5. Redis Caching

### الوضع

- لا حاوية Redis.
- `CACHE_STORE=database` يستخدم جدولي `cache`/`cache_locks`.
- إعدادات `REDIS_*` موجودة كقوالب Laravel فقط.

### مرشّحات تخزين مؤقت

| البيانات | مفتاح مقترح | TTL مقترح | إبطال | ملاحظات اتساق |
| --- | --- | --- | --- | --- |
| قائمة فئات | `categories:page:{n}` | 60–300s | عند `POST /categories` | آمن نسبياً |
| قائمة منتجات حسب فئة/صفحة | `products:cat:{id|all}:page:{n}:per:{p}` | 30–120s | عند إنشاء منتج (وبعد تحديثات مستقبلية) | **لا تضمّن كمية المخزون** |
| تفاصيل منتج (حقول MySQL فقط) | `product:{id}:meta` | 60–300s | عند تحديث المنتج | الكمية تُجلب حية أو تُستثنى من ETag المشترك |
| عدّادات عامة | بحذر | قصيرة | إبطال صريح | قد تتحمّل التقريب |

### ما يجب عدم تخزينه كمصدر سلطة

- **`available_quantity` كمقدار سلطة للشراء:** التخزين المؤقت قد يعرض كمية قديمة ويقود إلى سلال مضللة. الرفض النهائي يبقى عند `ReserveStock`، لكن تجربة المستخدم تتدهور وقد يفشل checkout بكثرة.
- بيانات خاصة بالمستخدم (طلبات، سلة، JWT claims) في مفاتيح مشتركة.

### تصميم الإبطال

- عند `ProductService::create` / اكتمال النشر: نسيان مفاتيح القوائم + مفتاح التفاصيل.
- عند لا يوجد update product اليوم: خطط للإبطال مع أي endpoint تحديث مستقبلي.
- استخدم tags إن بقي المتجر Redis (`Cache::tags` مع Redis فقط — ليست مع database cache).

## 6. HTTP ETag

### الوضع: غير منفَّذ

### تصميم عملي مناسب للعقد الحالي

1. ابنِ تمثيلاً معياريًا لحقول المنتج المستقرة: `id,name,description,price,image,category,updated_at` — **بدون** `available_quantity` أو مع فصل واضح.
2. احسب ETag = hash قوي للمثيل (مثلاً sha256 للـ JSON الكانوني) أو استخدم `updated_at` + id إن كان كافياً.
3. Middleware أو منطق في `ProductController::show`/`index`:
   - أرسل `ETag` و`Cache-Control: private, must-revalidate` (أو public للقوائم العامة بحذر).
   - إن `If-None-Match` يطابق → **304** بجسم فارغ.
4. إن بقيت الكمية داخل نفس التمثيل فستتغير كثيراً وستنخفض فائدة 304؛ لذلك يُفضَّل فصل حقل المخزون أو endpoint فرعي للكمية.

## 7. خطة قياس k6

### نقاط النهاية الأنسب

| الأولوية | Endpoint | الهدف |
| --- | --- | --- |
| عالية | `GET /api/v1/products` | قراءة كتالوج + ترقيم |
| عالية | `GET /api/v1/products/{id}` | قراءة + gRPC |
| متوسطة | `GET /api/v1/categories` | قراءة خفيفة |
| متوسطة | `GET /api/v1/orders` (مع JWT) | قراءة بعد تضخم الطلبات |
| حذر | `POST /orders` | لا تخلطه مع قياس القراءة دون عزل مخزون |

### منهجية قبل/بعد

1. بيئة ثابتة: نفس حجم البيانات، نفس موارد Docker، تعطيل Xdebug.
2. تسخين (warm) مقابل بارد (cold cache).
3. سيناريوهات VU ثابتة (مثلاً 20/50/100) لمدة كافية لجمع ذيول.
4. مقاييس: throughput، error rate، **p50/p95/p99**.
5. أثناء الحمل: حدّث منتجاً (أو أنشئ منتجاً) وتحقق أن التمثيل/الكاش/ETag يعكس التغيير خلال سياسة الإبطال.
6. لا تخلط نتائج adversarial-qa مع نتائج أداء المتطلب 3 دون فصل السيناريوهات.

**لم تُولَّد أي أرقام في هذا التقرير.**

اختناقات قد تُفسد النتائج: `php artisan serve` أحادي العملية نسبياً، gRPC على تفاصيل المنتج، أقفال MySQL الطويلة أثناء الحجز، غياب replica تحت ضغط قراءة.
